# スライドの図と挿絵

AIが作る図の失敗は、ほぼすべて「いらない情報を足しすぎ」から起きる。スライドの版面は思っているより狭く、要素を足すより大きく見せるほうが伝わる。

## 描く前に決めること

図を主役にするか、文字を主役にするか、どちらかに決める。図が主役のスライドでは、文章を見出しと導入の1行までにとどめ、図を版面の幅いっぱいに使う。文字が主役のスライドでは、図を幅100〜330pxほどの挿絵の大きさにして隅へ置く。両方を立てようとすると、図は小さくなり本文も詰まってしまう。

仕組みの図は1スライドで完成させず、同じ図を3〜5スライドに割って要素を1つずつ足していく。聞き手の負担が減り、話し手も説明の順序に迷わなくなる。

箇条書きの項目どうしに階層や分岐があるなら、図にする。「AとBは全員が行い、CとDはどちらかを選ぶ」のような関係は、同じ深さの箇条書きでは対等な選択肢に見えてしまう。図にするかどうかは、矢印か囲みを描きたくなるかで判断する。図へ描き出してみると、書き手自身の理解の誤りにも気づきやすい。箇条書きを図へ移したら、そのスライドの結論の箱は外す。図が主役になるため、箱とぶつかってしまうからだ。

骨子や初版を見せる段階から、説明のスライドは図で組んで出し、「図は後で入れる」として文字と表だけの版を見せないようにする。講義のスライドは図が主役なので、文字だけの版は中身が合っていても品質が低いと受け取られる。説明のスライドは「見出し＋1行＋版面いっぱいの図」を既定にし、図の要点を表す挿絵も最初の版から入れておく。

デッキを組んだら、図も画像も無い本文スライドを数える。流れ・分岐・対比・分担・繰り返しを文章で書いているものは、見せる前に図へ直し、本文は図の意味を伝える1行までに減らす。ただし、文を箱と矢印へ置き換えただけの図では足りない。描く前に、図ごとに「文では伝わらず、絵なら伝わるもの」を1つ決めておく。たとえば、量の差なら高く積んだ書類の山と数枚の紙、待ちの有無なら長い行列と空いた窓口といった具合だ。図の主役には、そこで起きている働きを正確に表すラベルを付ける。
画面の機能や仕組みも、文だけのスライドでは説明しない。「どの数字も元のファイルの行までたどれる」のような機能は、スクリーンショットか、画面とファイルを並べた簡単な図で見せ、文は図の下の1〜2行にとどめる。文だけだと、聞き手は何の話か思い浮かべられない。

図の説明を、図の下の小さい添え字や次のスライドの文で済ませてはいけない。箱ごとに2行の添え字を付けたり、「②を直す」のように前の図の番号を引いたりすると、文字が読めないうえに聞き手が前のスライドを思い出す手間がかかる。パラパラ漫画の要領で同じ図を数枚続け、1枚ごとに注目する所だけ濃くして他を薄くし、吹き出しの位置を動かして視線を運ぶ。説明の文は吹き出しの中の1〜2行へ移し、図の外に小さい文字を残さないようにする。

### 図の形は中身の種類で選ぶ

図を描く前に、その図で何を見せるのかを下の表から1つ決め、それに合った形で描く。数量も割合も範囲も日付も角丸の箱にしてしまうと、デッキ全体が同じ見た目になる。箱と矢印は、手順が一方向へ流れる図を描くときに使う。

| 見せたいもの | 形 | 描き方 |
|---|---|---|
| 数量（全体のうちいくつか） | 点の並び | 1つを1粒で並べ、対象外の粒は破線の白丸にする。境目に線を1本引く |
| 全体に占める割合 | ドーナツ | 輪の中央に全体の数を置き、右に内訳を大きい数字で並べる |
| 並んだ選択肢のどこに合わせるか | つまみ | 1本の線の上に選択肢を点で置き、選ぶ1つだけ大きい丸にする |
| 一方通行とくり返しの違い | 直線と輪 | 手順は直線の上の点、くり返しは輪の上の点にする |
| 強さや量が段階的に上がる並び | 坂 | 右上がりの面の上に項目を置き、両端に軸の言葉を書く |
| 範囲の包含 | 同心円 | 内側ほど濃く塗り、名前は引き出し線で外へ出す |
| 日付や時期の前後 | 時間軸 | 1本の線の上に期間を太い線で置き、切り替わりの日を縦の破線で示す |
| 手順が一方向へ流れる | 箱と矢印 | 箱を升目に並べて矢印でつなぐ |

- 図を描き始める前に、デッキの全図について「見せたいもの」と形を1行ずつ書き出し、箱と矢印が半分を超えていたら描く前に持ち替える。余白や配色の直しを重ねても、形が同じなら単調さは残る
- デッキを組んだら、図のあるスライドを並べて形を数える。箱と矢印の図が3枚続いたら、表に当てはまる中身が無いかを見て持ち替える
- 変化を付けるためだけに無理に別の形を当てず、中身がその種類に当たるスライドだけ形を変える。クイズのように同じ型をくり返すスライドは、形を揃えたままにする
- 色・書体・挿絵はテーマのまま保ち、形だけを変える
- 丸・輪・坂は、縦横の比を変えると歪む。図を版面に合わせて伸び縮みさせる処理があるなら、対象から外す
- 線や面の近くに置くラベルは、線から20px以上離す

### 手順のスライド

操作手順のスライドは、最初から「左に説明、右に実機のスクリーンショット」の2カラムで組む。文字だけの手順が続くと単調になる。スクリーンショットがまだ撮れていない段階でも、破線の枠と「何を撮るか」の1行を置き、撮影リストを残しておく。撮れたら枠を画像へ差し替える。

- 左カラムの幅は％ではなく px で固定し、改行は意味の切れ目で手で入れる。％で指定すると、本文が「スクリーン／ショット」のように語の途中で折り返してしまう
- 右の枠は絶対配置にして、高さを左の本文に合わせる。枠が低いと、下だけが大きく空く
- 話し手が撮ったスクリーンショットは原寸のまま載せる。切り取るのは範囲を指定されたときだけにする。ブラウザの枠やサイドバーは「どの画面のどこか」を伝える情報なので、切ると参加者が自分の画面と見比べる手がかりが失われる。範囲を指定されても、指定された端より内側で切らない。収まらないなら、余白か縮尺で調整する
- 窓の影の透過部分は背景色で埋め、外枠は付けない。背景から浮かせたいときは影と角丸だけにし、白い地と余白で額縁のように囲まない。アプリの窓はもともと縁を持っているので、白い縁を足すと縁が二重になる
- 押す場所は枠で囲んで番号を振り、順に矢印でつなぐ。元の画像に描き足すだけにして、切り抜きと組み合わせない

## 情報量の規律

足す前に「これが無いと図が読めなくなるか」を確認する。「あると親切」で足した要素が、かえって図全体を小さくしてしまう。

- 1スライドに載せるのは1テーマまでにする。前提条件、後続フェーズ、キーメッセージの帯は別のスライドへ分ける
- 同じことを二重に書かない。段の見出しとアイコンと矢印が同じことを言っているなら、見出しを消す
- 箱の名前の下に説明のサブラベルを入れない。「CDN／配信の入口」のような名前と説明の2段組みは、機械が作った図の典型的な見た目になる。名前だけで十分伝わり、説明は口頭で補う
- 図の中に注記の文を入れない。図は図形と短いラベルだけにして、言いたい文は本文へ出す
- 矢印の下や図の隅に説明の文を書き込まない。製品名の箱は名前だけで伝わる。説明は口頭へ回す
- 横並びの要素が4つを超えたら、関係の近いものを同じ薄い背景で包んでまとめる。人が一度に追えるのは3つ前後までだ
- 差し戻されたら、中身ではなく骨格を疑う。前の版のレイアウトを残したまま直すと、直すたびに情報が増えて密度が上がる

### 並べるのは3つまで、線は直線

- 図・表・箇条書きで並べる項目は3つまでにする。4つ以上になるなら、まとめるか外すかして3つに絞り、残りは本文の1行で触れる。項目が増えるほど文字が小さくなり、どれも読まれなくなる。「4つの柱」のように、その節の骨組みになっている数は例外とする
- ただし、使い始める入り口や対応環境、プランのように、聞き手がそこから自分の分を選ぶ選択肢の全体は、削らず全部並べる。本文の1行へ逃がすと「自分の使っているものが無い」と読まれる。5つ並べるなら、1項目を短い名前と1語の補足にして文字の大きさを保つ
- 図の線は直線と直角で引く。曲線を伸ばして点や丸につなぐ装飾は使わない。要素を包んだりまとめたりしたいときは、土台の帯や入れ子の円で表す
- 経路の分岐や1対Nの役割分担のように、1つから分かれる線や1つへ集まる線は、曲線で引いてよい。出発点と到着点をそれぞれ1点にそろえ、その点を絵や箱の縦の中心に置く。線の本数で数の関係を見せ、両端で並び順をそろえて交差させない。直線で無理に引くと、矢印の高さが絵とずれる。1枚で線のずれが見つかったら、線のある図を全部並べて同じずれを探す
- 図を置いたスライドに、理由の無い空白を残さない。丸や点の一覧は左右や下が空きやすい。横幅いっぱいの面にするか、リード文を1行足して版面を使い切る

### 削りすぎない

詰まりを直すときに、全部を「1行ラベルの箱と矢印」へ均さない。削りすぎると、どこにでもある簡素な図になり、その図だけの見せ方が消える。消すのは細かい文字だけにして、形は残す。

| 消す（詰まりの正体） | 残す（その図の個性） |
|---|---|
| 箱の中の2行目の説明文 | 年表、件数の横棒、ユニットチャートのような、その図だけの見せ方 |
| 図の中の題名・前置き・下の注記・凡例の説明文 | 1つから6つへの枝分かれや往復の矢印のような、構造そのものを見せる線 |
| 本文と同じ数字や列挙の二重書き（図の主役になっているなら残す） | 主体や場面を一目で伝える挿絵（1枚に1点まで） |
| 装飾だけの枠・影・グラデーション | 主役の数字1つ |

- 残すかどうかは「文字か、形か」で判断する。小さい文字は削る。グラフ・年表・枝分かれ・挿絵は、本文と内容が重なっていても図の見どころなので残す
- 骨格を疑うのは、中身を足し続けて密度が上がったときの話だ。骨格ごと捨てて汎用の型へ置き換えるのは、別の失敗になる
- 1枚ずつ「この図にしか無い見せ方」を1語で言えるか確かめる。言えなくなったら削りすぎている
- 戻すときは、元の図を土台にして文字だけを抜く。汎用の型で組み直してから要素を足し戻すと、元の図の比率や構図が戻らない
- 次の型も、それだけで機械が整理した図に見える
  - 「削除／維持／追加」のように、区分名と中身を書いた札を3つ横に並べる。差分は、本体の上に取り消し線と色で直接見せる
  - 同じ形の箱を縦に6つも7つも並べる。枝分かれの形は残し、枝の先は箱にせず短い語だけにする
  - グラフの中で1点だけ、デッキの色と別の強調色を混ぜる。1つの色相の濃淡とグレーで描く

### 構成図

- ブラウザやアプリといったクライアントを1つのノードとして描く。人のイラストからクラウドへ直接線を引くと、画面の存在が消える
- アイコンを「役割ごとの箱」に入れない。箱に入れた時点で、描けるのは箱どうしの関係だけになる。囲ってよいのは、アカウントやネットワークのような実在する境界だけにする。ただし実在する境界でも、一部の機能だけ別のアカウントから呼んでいるといった提供側の内部都合で、読み手が判断に使わないものは別の箱にしない。1つだけ別の箱に入れると、そこだけ管理が別だと読まれてしまう。海外のリージョンを使うといった、読み手に伝えるべき違いは名札の文字で書く
- スコープの外も描く。既存環境や後続フェーズは薄いグレーで置き、範囲外であることを示す
- 矢印は実装どおりに引く。「画面 → API → データ」の直列を仮定せず、権限の設定とフロントエンドの呼び出し先を読んでから引く。実際に権限を持って他を呼ぶ主体を図の中心に置くと、絵の中心と説明の主役が一致する
- 1つの起点から放射状に伸びる線に、線に沿ってラベルを置かない。必ず線が文字を貫く。ラベルは、その線が通らない帯へ置く
- 配線は升目で組む。列と行の中心を先に決めてアイコンを交点に置き、線は水平と垂直だけで引く。1つの起点から複数の経路へ分けるときは、起点の横に縦の幹線を1本立てて各行へ水平に分ける。線の端はアイコンの辺の中点に着け、角に斜めから刺さない
- データベースは物理の単位を名指しする。技術者の読み手に「3つの層」のような概念だけを見せると、インスタンス・データベース・スキーマ・テーブルのどれが分かれているのか分からない。外枠にエンジンと台数を書き、層がスキーマなのかテーブル名の接頭辞なのかを明記し、各層に実物のテーブル名を並べる
- クラウドのアイコンは公式のアイコンセットを使う。似た色のブランドロゴで代用しない。製品名を略して別の製品と同じ表記にしない
- ストレージ・データベース・分析基盤・BIツールといったクラウドの製品が出てくる図は、名前の箱で済ませず公式のサービスアイコンを置く。AWS 以外も同じで、Azure は Microsoft Learn の「Azure architecture icons」、Power BI は Microsoft Fabric の公式アイコン一式に入っており、Power Platform の一式には入っていない。どちらも図や研修資料での利用が許されており、切り抜き・反転・変形は禁止されている
- 実行基盤となるインフラは、上に載るものの下に敷く土台として描く。載るものを箱で並べ、ラベルに基盤の名前を書くだけでは関係が伝わらない。呼び出しのプロトコルといった載るもの同士の関係は、土台の上で矢印と札でつなぐ。実際に別々のインスタンスなら、土台も1つずつ分ける。1本の長い土台にすると、全部が同じ基盤に載っているように伝わる
- 手持ちに無いアイコンを、四角や記号を描いて自作しない。サービスのアイコンと、ブラウザ・ユーザー・フォルダなどの汎用アイコンをそろえた公式の一式を手元に置き、ファイル名で引いて、使う分だけ資料のフォルダへコピーしてから埋め込む。別のリポジトリのパスに依存させない。他社のサービスはロゴを作らず、汎用アイコンとサービス名の文字で表す

### 2軸の図（4象限のマトリクス）

- マスは全部同じ淡い面にし、載せる名前は同じ形の濃い札にする。白抜き文字の濃い箱と、濃い文字の淡い箱を1枚に混ぜると、読み方がそろわない
- 1つのマスに名前を2つ入れるなら、2行の文字ではなく札を2つ並べる。2行だと改行なのか列挙なのか分からない
- マスの隅に小さい注記を置いたり、マスの色を少しずつ変えて意味を持たせたりしない
- 空きのマスも同じ淡い面にして、札が無いことで空きを示す
- 矢印を引くなら、横切る面と明度の離れた色にする。濃い箱どうしの間に暗い色の矢印を引くと見えない
- 札の色はデッキのほかの図と同じグラデーションにそろえる。出す前に `rg -o 'fill="#[0-9a-fA-F]{6}"|stop-color="#[0-9a-fA-F]{6}"' images/*.svg | sort | uniq -c` で他の図の配色と並べる

## 機械っぽさを消す

- アイコンを絵文字で済ませない。登場人物や物はイラストか実物のアイコンで描く
- 人物は「ユーザー」と書いた角丸の箱ではなく、イラストを1枚置く
- 箱の中は大きめの1行ラベルを基本にし、「タイトル＋サブタイトルを枠で囲った箱」を並べない
- 強調は太い枠ではなくベタ塗りで付ける。階層は「ベタ塗り（主役1つ）、暗い塗りで枠なし（通常）、枠線のみ（脇役やモノ）、薄い背景（ゾーン）」の4段で作る
- 図の面の色は、スライドの背景色に合わせる。中間色のレーン背景を勝手に敷かない
- 白地用の図の色だけを機械的に置換した図は、枠線とサブテキストの構造がそのまま残る。ベタ塗りと1行ラベルの型で作り直す
- 縦長の帯や大きい図形に置く文字は、縦中央に揃える。上端に寄せると浮いて見える
- 左右に分けたページの本文と画像は上揃えにし、見出しの直下から始める。縦中央に揃えるのは図形の中の文字だけで、本文を縦中央に置くと浮いて見える
- アイコンは高解像度の原本から取る。小さいスクリーンショットからの切り出しを拡大するとぼける
- 余白を残す。詰めて収めるより、箱を大きく、間隔を広く、要素を少なくする
- 名前・ハンドル・イベント名・ラベルといった、全ページに繰り返す小さな飾り文字をヘッダーやフッターに入れない。名前とハンドルは表紙と自己紹介で1回ずつ出せば足り、締めのスライドでも繰り返さない
- 「モダンにして」と言われたとき、メダル・マイク・王冠のような線のアイコンをラベルやチップの頭へ添えて応えない。記号アイコンを文字の頭に並べるのは、機械が作った画面の典型的な飾りになる。今風にするには、影を外して淡い面で平らに塗ったりグラデーションの細い線で囲んだりする面の塗り方と、文字の色だけで調整する。「アイコンにして」と頼まれても飾りなしの案を先に並べ、アイコン案は入れても1案までにとどめる
- 括りの線の上の言葉や列の見出しなど、図の中の見出しは面を敷かない地の文字にし、文字の下端と線・箱の間を30px以上あける。面を敷いたラベルは、すぐ下の線に貼り付いて見える。ラベルの形が要るのは、その言葉が図の部品として独立しているときだけだ
- 左から右へ「これを受け取る→これができる」のように対応させる図は、両側を同じ形の箱にし、結果の側を濃い面にする。列の見出しは、その列の箱の中央に揃える。片側だけ箱で、もう片側が素の文字だと、図が描きかけに見える
- 大きな文の前後に、小さい文字を飾りとして並べない。タイトルの上の小さな英字ラベル、見出しや吹き出しの下の薄い補足行、途中から2段3段と小さくしていく文字は、どれも機械が作った資料に見える。言うことは1つの文にまとめ、文字の大きさは多くても2段にする。テンプレートを使わない1枚ものの紹介スライドでも同じだ

## SVGの実装

### 文字サイズ

図の中の文字は、書き出したPDFの実寸で16pt以上にする。会場の後ろの席から読める下限だ。SVGのソースに `font-size: 21px` と書いてあっても、Marpで `![center w:820]` と縮めて貼れば13ptになる。目安として、viewBoxの幅が1000のSVGを `w:1000` で貼るなら、箱のラベルは19〜22pxにする。

文字と箱の縁のあいだは14px以上あける。箱の中の文字は、周りの余白とセットで設計する。窮屈さと左右・上下の偏りは、図を作るたびに出やすい。箱を広げるだけで済ませず、文字を減らして余白を作る。書き出す前に `tools/check-svg-box-fit.mjs` で実測する。

収まらないときは、文言を短くする、箱を広げる、図の幅を上げる、font-sizeを上げる、の順で直す。長い文言を大きくしても箱に入らない。文言を削れば、同じ箱で13ptから17ptまで上げられる。

### 文字が箱に収まるかは実測する

ソースの数字から「この幅なら収まるはず」と計算しない。実際の字幅はソースに書かれておらず、`font-size × 文字数 × 0.6` のような見積もりは2割ほど外れる。縮小したページ画像を見て「収まっている」と判断するのも、同じくらい当てにならない。数pxのはみ出しは見えない。

描画してから `getBBox()` で測る。その処理は `tools/check-svg-box-fit.mjs` が行う。

箱の中にアイコンを入れると、そのぶん文字が押し出される。飾りのアイコンなら外すのが正解で、フォントを1〜2px下げても解決しない。

### 矢印

SVGの `<marker>` は既定が `markerUnits="strokeWidth"` なので、矢尻の実寸は markerWidth × stroke-width になる。8 × 4 なら32pxで、42pxの線の両端に付けると軸が消えて矢尻だけが残る。

- 矢尻は `markerUnits="userSpaceOnUse"` で18px前後に固定する
- 線は矢尻の3倍以上の長さを取る
- ラベルは矢印から10px以上離す
- 図形が近すぎると、矢印の軸が隠れて矢尻しか見えなくなる
- 番号バッジ・矢印の札・名前は、線とも他の文字とも12px以上離し、線の上に置く札は14pxを目安にして、線との隙間を全部の図でそろえる。重なりだけを見る検査は、線に張り付いた札を通してしまう。1か所見つけたら、全部の図で同じ状態の箇所を直す

### グラデーション

- 水平または垂直の線の `stroke` にグラデーションを指定すると、線が描画されない。線のbboxの片方の辺が0になり、`objectBoundingBox` のグラデーションが定義できないからだ。線と `marker` の中は単色にする。斜めの線と曲線には使ってよい
- 複数の箱をまたいで1本のグラデーションを流すなら `gradientUnits="userSpaceOnUse"` にして、`x1` と `x2` に図全体の座標を入れる。既定のままだと箱ごとにグラデーションが完結して、同じ柄が繰り返される
- 色を一括置換すると、`marker-end:url(#id)` のid文字列まで書き換わって矢尻が消えることがある。置換したら矢印の先端まで目で確かめる
- `<text>` の `fill` にグラデーションを指定しない。PDFへ書き出すと文字の形が失われ、文字の外接矩形がそのまま塗られて色の塊になる。縮小画像では気づけないので、拡大して確かめる。図の中の文字は単色にし、グラデーションは面の塗りだけに使う

### その他

- 図の上下の空白は `viewBox` で切る。`viewBox="0 50 1000 320"` のように中身の無い帯を落としてから幅を上げる
- 図の中で数字を並べるときは、フォントサイズとベースラインを明示的に揃える
- 色の明度が近い2色を隣り合わせない。片方を薄い地に濃い文字、もう片方を濃い地に白文字にする
- 図の中の要素どうしの接触は座標で検算する。吹き出しのしっぽの先と隣の絵、ラベルの両端と隣の要素のあいだに10px以上を確保する
- 自作の図は、生成スクリプトの中で要素どうしの隙間を測る。画像・文字・矢印・札の外接矩形を記録し、どの2つも14px以上（ラベルと補足の2行は8px以上）離れ、枠から6px以上内側にあることを、書き出すたびに検査する。矢印は四角で近似せず、線分との距離で測る。画面の中のロボットのように意図した重ね置きだけを対象外にする。目分量で置いた図は「詰まっている」「くっついている」と全面のやり直しになる

## コードに補足を付ける

コードのスライドは、コードを主役にする。小さいコードブロックの前後に説明文を足すと、余白は多いのに文字がびっしりの画面になる。

- コードの文字を大きくし、版面の幅いっぱいに使う。本文は見出しの下の1行だけにする
- キーワードと文字列など、構文の色は2色までに絞る。関数名・クラス名・変数まで塗り分けると、色が散って読みにくい
- コードと補足の区別が付かなくなるため、補足はコードの中のコメントに書かず、行ごとの帯の強調もしない
- コードを1枚の画像のように扱い、その上に横向きの吹き出しを重ねる。吹き出しの箱から斜めに伸びるしっぽで、指したい行を指す
- 吹き出しはコードが青系ならオレンジや赤といった別系統の色のベタ塗りにし、文字は白の太字にする。同系色だとコードと補足が見分けにくい
- 吹き出しを傾けたり箱に矢印を付けたりせず、しっぽだけを斜めにする
- 吹き出しは指す行のすぐそばの空きに置き、しっぽを短く保つ。空きが無ければコードの側に空行を足す
- 位置は目分量で決めず、`mutool draw -F stext` で取った書き出し済みPDFの行の座標から、しっぽの先の座標を決める
- 吹き出しの層は、スライド全面の大きさの透明なSVGを作って重ねる。Marp の書き出しは `data-*` 属性を落とすので、位置や見た目はクラスで指定する
- 文言は「ここで保存する」「戻り値はこの形」程度の短い1句にする

## 挿絵

### 入手

作者は「いらすとや」の素材をよく使う。画像はこのリポジトリに同梱していないので、必要なものを都度サイトから取得する。

1. `https://www.irasutoya.com/search?q=<語>` で探す。「ロボット」のような見た目の語より、「AI 会話」のような用途の語のほうが当たる
2. 記事ページを開き、画像の直URLを確かめる
3. `curl -sL -o "images/irasutoya-<内容>.png" "<直URL>"` で保存する

点数の上限や禁止される使い方などの利用条件は、いらすとやの「ご利用について」で各自確かめる。

素材をまとめて探すときは、検索結果のHTMLから一覧を抜くと速い。検索結果の各エントリは `bp_thumbnail_resize("<画像URL>","<タイトル>")` の形で埋め込まれていて、記事を開かずにタイトルと画像URLが取れる。URLの `s72-c` を `s800` に替えると大きい画像になる。

```bash
curl -sL -A "Mozilla/5.0" --get --data-urlencode "q=会話" "https://www.irasutoya.com/search" -o page.html
rg -o 'bp_thumbnail_resize\("[^"]+","[^"]+"\)' page.html | head -8
```

- 2語以上で検索すると0件になりやすい。1語で引いて一覧から選ぶ
- タイトルが「いろいろな〜」のエントリはセット画像だ。個別の画像は記事の中に並んでいる
- 取った素材は一覧画像に並べて見る。透過PNGは白地に合成してから縮小する。そのままでは黒く潰れて見えることがある

手元に保存した素材が色落ちしていたり低解像度だったりしたら、着色や拡大でごまかさず、元の記事を探して取り直す。

過去に切り出した素材が、無彩色に変換されたまま残っていることがある。納品前に、デッキが使う画像の彩度を数え、色の無いものは原本を取り直して比べる。書類の山のように原本がもともとモノクロなら、そのまま使う。

```bash
python3 -W ignore -c "import re,sys;from PIL import Image
md=open(sys.argv[1],encoding='utf-8').read()
for u in sorted(set(re.findall(r'\./images/[^\")\s]+\.png',md))):
    im=Image.open(u[2:]).convert('RGBA');im.thumbnail((300,300));px=[q for q in im.getdata() if q[3]>200]
    r=sum(1 for a,b,c,d in px if max(a,b,c)-min(a,b,c)>25)/max(len(px),1)
    r<0.02 and print(round(r,3),u)" deck.md   # デッキのフォルダで実行。色の無い画像だけが出る
```

### 選び方

絵が本文の名詞そのものを描いているかで決める。「待つ」のスライドに待つ人、「馬車」の比喩に馬車、は通る。AIっぽい、仕事っぽい、OKっぽいといった雰囲気合わせで選んだ絵は全部外す。合う絵が無いスライドには置かない。

選ぶ前に「このスライドの要点は何か」を1行で言い、その場面が描かれた絵を検索語にする。たとえばAIが資料を検品した振り返りなら、「虫眼鏡で調べる人」を探す。手元の素材フォルダから選ぶのは、要点に合う絵がそこにあるときだけにする。OKサインやガッツポーズのように、どのページにも置ける汎用の絵を埋め草にしない。デッキをまたいで同じ絵に偏っていないかも数える。

```bash
rg -o --no-filename 'irasutoya-[^")\s/]+\.png' slides/ | sort | uniq -c | sort -rn | head
```

人物の格を本文の意味に合わせる。「優秀な部下」の喩えに、やんちゃな子どもの絵を置かない。

OKサイン、ガッツポーズ、笑顔といった肯定的な絵は、本文が肯定的な結論のときだけ置く。課題や不満を並べたスライドに置くと、トーンが逆になる。1枚を差し替えるときも、元の絵を選んだ理由ではなく、いまの本文を読み直してから探す。

事例、製品、リポジトリを紹介するスライドは、挿絵ではなく実物のスクリーンショットを使う。

### 入れる数と位置

- 表・図・コードなど目を引く要素があるスライドには入れない。挿絵を置くのは、文字だけで殺風景になるスライドに限る。右下が空いていることは置く理由にならない。空きで判断すると、デッキ全体では多すぎて煩わしくなる
- 毎スライドに置かない。作者の例では、49スライドのデッキで挿絵は6か所が適量だった。13か所に入れたときは多すぎた
- 同じ位置に連続させない。前半だけ、後半だけにも偏らせない
- 同じ絵を2回使わない。納品前に数えて、2以上が出たら差し替える：`rg -o 'irasutoya-[^."]+' deck.md | sort | uniq -c | sort -rn | head`
- 基本の位置は右下の空きにする。右下が空いているのに左上へ置いて図形と重ねるのは逆効果になる
- 位置を散らしてメリハリを付けようとしない。挿絵は右側に揃えたまま、長い箇条書きを意味の切れ目で改行して2行に割る。すると右側に縦長のくぼみができ、そこへ挿絵が収まる
- 挿絵の右端は、本文の左右余白より内側へ入れる。本文の余白が96pxなら、挿絵は118pxにする
- 横に長い締めの文があるスライドでは、左下に置かない。文の右端が版面いっぱいまで伸びて重なる
- 縦長の素材は幅を100〜120pxに抑える。幅190pxでも高さが380pxになり、上の要素へ食い込む
- 挿絵と吹き出しや枠は、ペアで位置を動かす
- 図の中で挿絵に文を添えるときは、挿絵と文を横に寄せて1つのまとまりにし、まとまりごと中央へ置く。挿絵を図の端、文を中央に離すと、挿絵が浮いて見える。カードを横に並べる図は、カードの中に番号・挿絵・名前・数を縦に収め、版面の横幅いっぱいに広げる
- 図は詰め込まない。並んだ箱どうしは図の座標で28px以上、文字の行どうしは文字の高さの半分ほど空ける。版面に収まらないときは、隙間を削らず、図を少し縮めるか項目を減らす
- 塗った地の上に、別の色で塗った箱を重ねない。灰色の地に薄い青や灰色の箱を置くと境目が見えない。まとまりを示したいときは、塗らずに細い線で囲む。ただし吹き出しのように形そのものに意味がある囲みは、線で縁取らず薄いベタ塗りにし、中の箱の色のほうを地と見分けがつく濃さへ調整する。縁取りの中に箱が並ぶと線だらけになる。表のような図でまとまりを区切るときは、罫線ではなく、見出しの列に敷いた薄い面の切れ目で区切る
- まとまりを線の枠や吹き出しで囲むときは、枠と中の箱の間を14px以上あけ、枠の外に添える括弧や説明は枠から18px以上離す
- 出来上がった図に要素を足すときは、足す前に外す要素を決め、間隔を全体で割り付け直す。囲み・挿絵・ラベルを元の配置の隙間へ差し込むと、足した要素のまわりだけ詰まり、組と組の区切りも消える。組の中の間隔より組の間の間隔を広く取れているかを、書き出した画像で確かめる
- 挿絵や図と、すぐ上の文字は30px以上あける。下に置く図の名前のラベルは図に寄せ、ラベルと次の文字の間を広く取る
- 収まらないときは、余白と文字の大きさを守り、載せる量を減らす。項目を減らす、名前を短くする、補足の列を外す、の順に試す。隙間を詰める、文字を小さくする、細かく改行するといったやり方で無理に収めない
- 箱の中の文字は、縁から左右28px・上下18px以上あける。矢印や線とそのラベルは20px以上離し、矢印を入れる隙間は軸が見える50px以上にする
- 並べる図形は升目に置き、箱の幅・位置・端を全部の行と列でそろえる。続きのスライドは、前のスライドの図と同じ位置・同じ幅の骨格を使う
- 増減を見せる図は、塗った部分が階段の形になるように項目の順番を決める。層や帯のようにひと続きのものは、離さずくっつける
- 成功・注意・失敗のような意味の色は、原色のベタ塗りにしない。淡い面に、同じ色相の深い色の文字を載せる
- 区別を色で伝えるときは、縮小した一覧でも一目で分かる差にする。同じ色相のわずかな濃淡で分けない
- 1枚のスライドに載せる図は1つまでとし、補足のために図を足さない
- 箱のあるスライドでは、箱と重ならない位置を選ぶ。枠線はテキスト抽出に出ないので、機械検査をすり抜ける

### Marpでの書き方

`<img>` にインラインの `style` 属性を書いても反映されない。Marpのパーサーが属性を落とすためで、PDFを書き出して見るまで気づけない。大きさの違うクラスを用意しておく。

```css
.ill { position: absolute; right: 118px; bottom: 200px; width: 200px; }
.ill.sm { width: 160px; bottom: 95px; }
.ill.md { width: 180px; bottom: 110px; }
```

`bottom` の値はスライドごとに、本文の下端からスライドの下端までの空きを測って決める。

## スクリーンショットを載せるとき

- 自分たちのページやアプリの画面が古いデザインのままなら、枠だけ新しくして撮らない。中身まで今の型で作り直し、公開し直してから撮る。古いページを撮ると、新しいデッキの中でそこだけ古く見える
- ロゴや名前、ページのタイトルなど、何のページか分かる見出しを入れて切り、中身が読める大きさまで拡大する。ページ全体を縮めて載せると、何の画面か分からず字も読めない。一覧なら見出しと最初の数件だけを切り出し、ページの片側に大きく置いて、文は反対側へ回す
- 聞き手が「いつものあの画面だ」と分かる範囲と、そのスライドで言いたいことの両方が入るように切る。比較のページなら説明と実物を上下に並べた所、レポートならタイトルと要約の所を入れる。結果の部分だけや、スマホ幅の細い切り抜きにしない。部品だけを並べたいときはページ上で要素を集め直し、PC幅で外側の余白ごと撮る
- 撮るときはビューポートを1280px前後にし、左右の余白が対称に残る範囲で切る。スライドへ縮めたときに本文の文字が読めるかも、書き出した画像で確かめる
- 「〜と頼むと、〜が並行に進む」のような画面の操作の流れは文字だけで説明せず、実際の画面か、似せた画面のモック画像を添える
- 設定ファイルなどの引用は、タイトルバーにファイル名を入れたエディタの窓の形で見せる。行番号は実物に無い数字になるので付けない
- PCとスマホの画面を並べた合成画像は、1枚のまま枠・影・角丸を付けて置かない。合成画像の余白ごと影が付き、後ろに透明な板があるように見える。画面ごとに切り出して別々の画像にし、それぞれに影を付けて大きく並べる。透過PNGなら `filter: drop-shadow` を使う
- 片側に画像・反対側に文を置くページでも、文の行頭は本文の左端にそろえる。ページごとに文を中へ寄せると、めくったときに行頭が揺れて見える。本文と画像の間と、まとまり全体の左右の空きもそろえる。間だけ広く空くと、真ん中の大きな空白に見える

## 物を本文に挟むときの余白

画像・引用の窓・吹き出し・表を文章の間に置くときは、物の上と下の余白を、段落と段落の間と同じ1行ぶんにそろえる。テーマや部品の既定の余白は物ごとにばらばらで、そのまま置くと物の前後だけ詰まり、上下で不揃いに見える。見出しの直下に箇条書きや図がすぐ来るページには、リード文を1〜2行はさむ。ただしパロディや中扉のように、元の型にリード文が無いページは除く。

吹き出しで画面や図を指すときは、しっぽの先を対象の端から14〜30pxに置く。くっつけると窮屈に見え、離しすぎると何を指すか分からない。吹き出しを端に寄せたまま画像を小さくすると、間が大きく空いて指す先が分からなくなる。

## 公開ページから図を借りるとき

いきなりDOMから画像のURLを抜いて直接ダウンロードしない。レスポンシブなサイトは同じ図の縦積み版と横並び版を両方持っていることがあり、URLだけ拾うと縦積み版を掴む。スライドは16:9なので、必要なのはほぼ常に横並び版だ。

1. ページを実際の幅で表示し、スクリーンショットを1枚見る
2. 候補の画像が複数あれば、全部開いてから選ぶ。縦横比が1未満の縦長を外すだけでも当たる
3. 切り取って情報を落とす前に、切り取らずに済む版が無いかを確かめる
4. 図が小さいときは、版面の下へ押し込めて縮めない。図の上の題字と周りの余白を切り落とし、大きく貼る

## 図を流用するとき

- 別のデッキから図を持ってくるときは、その図を含む全デッキを素材名やSVGのクラス名で列挙し、いちばん後に直された版を使う
- 本編に出てこないサービスのアイコンを持ち込まない。デッキごとに構成が違うと、資料の中で矛盾する
- 黒地のデッキの図を白地のデッキへそのまま貼らない。逆も同じだ。黒い四角が白い紙面に浮き、別の資料から切り取ってきたように見える。素材の原本を取り直し、貼る側の背景で図を組み直す。スクリーンショットの黒い余白も同じで、外周を背景色へ抜く
- 同じ見出しのスライドは、図の対応も含めて変えない。見出しは合っているのに図が別のスライドのもの、という取り違えは縮小画像では判別できない。`tools/check-reuse-diff.py` で流用元と突き合わせる
- 配色やテーマの載せ替え、検査への対応で図を描き直すときも、元の図の配置は変えない。枠からはみ出した要素、枠の外に置いた要素、重なりは、何を枠の内と外に分けるかを表す意味を持っている。検査に通すために枠を広げて収めたり位置をそろえたりしない。検査が止めたら、元の配置のまま余白や大きさで直すか、その要素を検査の対象外にする
- 構成図にbase64で埋め込んだアイコンは、正規表現で抜いてデコードすれば単体の画像として再利用できる
- 話し手の元の図がある図を描き直すときは、元の図を横に並べて見た目や作りを寄せる。矢印の太さ、色の濃さ、矢印どうしの間隔まで合わせる。循環を表す矢印は同じ円の一部として描く。ばらばらの曲線では、つながっている感じが出ない。意味が元の図から離れていないかも確かめる

## 書き出したら検査する

機械検査と目視は、見ているものが違う。両方やる。

```bash
python3 tools/check-figure-text.py deck.pdf          # 16pt未満の文字、箱の縁まで14px未満の文字
node tools/check-svg-box-fit.mjs images/*.svg        # SVGを描画して文字と枠の余白を実測
node tools/check-svg-spacing.mjs images/*.svg       # 箱どうし・行どうし・線や挿絵と文字の間隔、塗りの重ね
```

機械検査は「存在する要素」を測るので、要素が丸ごと描かれなかった崩れは検出できない。図を触ったページは150dpi以上で1ページずつ焼いて見る。見るのは、文字と図形の重なり、矢印の軸、線の合流部、枠の角、文字が箱からはみ出していないかといった点だ。

1つの図を指摘されたら、同じデッキの全図へ同じ検査を当ててから直す。指摘は1つでも、同じ条件に当てはまる図はたいてい複数ある。

書き出した図を見て、線が多い、色が濁る、形がそろわない、のように自分で引っかかった点があれば、検査が通っていても、直す案を1つ決めて反映するか、案として添えて出す。指摘されてから直す流れにしない。

報告には、`check-figure-text.py` OK、全ページ目視 OK のように、通した検査の名前をそのまま並べる。「書き出しました」だけでは、通していない検査が見えなくなる。
